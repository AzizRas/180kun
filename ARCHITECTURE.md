# Архитектура

## Это микросервисная архитектура? Да — по свойствам, нет — по развёртыванию

Требование звучало так: «убрать или добавить модуль и чтобы ничего не
слетело». Из того, что даёт микросервисная архитектура (MSA), здесь есть всё,
что относится к **независимости частей**:

| Свойство MSA | Как сделано здесь | Чем проверено |
|---|---|---|
| Сервис владеет своими данными | Модуль читает и пишет только таблицы со своим префиксом; `UserData` отвергает чужую таблицу | тест «модуль не может стереть чужую таблицу» |
| Общение только через API и события | Шина событий + контракты в `app/Contracts`. Ни одного прямого вызова соседа | правило 1 в CLAUDE.md |
| Отказ одного не роняет остальных | У каждого контракта есть заглушка; упавший слушатель пишется в журнал, издатель продолжает | 6 сценариев в `smoke.php`, где половина модулей выключена |
| Сервис включается и выключается отдельно | Одна строка в `modules.php` | те же сценарии |
| Своя схема БД и миграции | `modules/<Имя>/Migrations`, учёт по модулям | автомиграции |
| Замена реализации без изменений у соседей | Контракт → другая реализация (ИИ-провайдер, SMS-шлюз, оплата, видеосвязь) | `LlmClient`, `Gateway`, `Access`, `CallProvider` |

Чего здесь **нет** — отдельных процессов, сети между ними, своей базы у
каждого сервиса и оркестрации. Это сознательно (решение Т-01): на хостинге
за $2–3 и на одном контейнере Railway такое не запускается, а для одного
разработчика умножает работу в разы. Такой подход называется **модульный
монолит**: границы как у микросервисов, развёртывание — одна папка.

**Когда модуль пора вынести в настоящий сервис** (например, тренер при
тысячах пользователей или медиа на своём сервере): его `Domain/` переезжает
как есть, таблицы с его префиксом — в свою базу, а на месте остаётся
реализация того же контракта, которая ходит по HTTP, и мост, пересылающий
его события. Остальные модули изменений не заметят: они и раньше знали
только контракт и события. Именно для этого правило «никаких JOIN через
границу модуля» соблюдается без исключений.

## Три уровня

```
┌──────────────────────────────────────────────────────────┐
│  index.php — единственная точка входа                    │
└───────────────────────────┬──────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────┐
│  ЯДРО (app/)  не знает ни одного имени модуля            │
│  Kernel · Container · ModuleRegistry · Events · Router    │
│  Db · Migrator · I18n · Request · Response · Result       │
│  Contracts/ ──── интерфейсы + безопасные заглушки         │
└───────────────────────────┬──────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────┐
│  МОДУЛИ (modules/)  между собой — только события          │
│                     и контракты                           │
│  Health · Identity · Telegram · Sms · Web · Onboarding ·  │
│  Planning · Checkin · Gamification · Squad · Wearable ·   │
│  Coach · Safety · Billing · Admin · Analytics  (16)       │
└──────────────────────────────────────────────────────────┘
```

## Анатомия модуля

```
modules/Squad/
  module.json         паспорт: имя, версия, зависимости, какие события
                      публикует и слушает, префикс таблиц
  Module.php          register() — свои сервисы в контейнер
                      boot()     — подписки на события
  routes.php          свои HTTP-маршруты
  Domain/             логика; ничего не знает про HTTP, возвращает Result
  Migrations/         001_init.sql, 002_… — только свои таблицы
  lang/ru.php
  lang/uz.php
```

Правило владения данными: модуль `squad` владеет таблицами `squad_*` и
только ими. Чужие данные берутся через контракт или приходят в событии.
Никаких `JOIN` через границу модуля — именно это позволяет вырезать модуль
целиком, не сломав соседей.

## Как модули общаются

**События — когда «сообщаю, что произошло».** Издатель не знает, слушает ли
его кто-нибудь, и не ждёт ответа.

```php
// модуль Checkin, ничего не знает про очки
$kernel->events->emit('checkin.recorded', ['user_id' => 7, 'done' => true]);

// модуль Gamification, подписался в boot()
$kernel->events->on('checkin.recorded', function (array $p) use ($kernel) {
    $kernel->container->get(Gamification::class)->award($p['user_id'], 'checkin', 10);
}, 'gamification');
```

Выключили Gamification — чек-ин продолжает работать, просто очки не
начисляются. Слушатель, бросивший исключение, не роняет издателя: ошибка
пишется в лог и видна в `/health`.

**Контракты — когда «нужен ответ».**

```php
$coach = $kernel->container->get(App\Contracts\Coach::class);
$reply = $coach->replyToCheckin($context);   // NullCoach вернёт шаблон
```

## Заглушки — техническая гарантия обещания

`app/bootstrap.php` регистрирует заглушку для каждого контракта **до**
загрузки модулей. Модуль, реализующий контракт, перекрывает её в `register()`.
Если модуль выключен, контейнер отдаёт заглушку, и приложение теряет
возможность, но не падает.

| Контракт | Реализует | Что делает заглушка |
|---|---|---|
| `Auth` | Identity | Возвращает «не авторизован» → защищённые маршруты дают 401 |
| `Coach` | Coach | Отвечает шаблонами, `isLive() = false` |
| `Notifier` | Telegram / Sms | Не отправляет, возвращает `false` |
| `Wearable` | Wearable | Отдаёт `null` по метрикам, `isConnected() = false` |
| `Gamification` | Gamification | Начисляет 0, отдаёт пустой профиль |

`/health` показывает по каждому контракту, кто его реализует и работает ли
он по-настоящему. Это первое, что нужно открыть после правки `modules.php`.

## Порядок загрузки

1. `bootstrap.php` — автозагрузчик, конфиг, контейнер, заглушки контрактов.
2. `discover()` — чтение `module.json`, проверка зависимостей, сортировка.
   Модуль с невыполненной зависимостью выключается, причина попадает в `/health`.
3. `register()` — модули кладут сервисы в контейнер. Обращаться к чужим
   сервисам здесь нельзя: они могут быть ещё не зарегистрированы.
4. `boot()` — подписки на события, маршруты, переводы. Здесь можно всё.
5. `handle()` — маршрутизация запроса.

## Ошибки

Ожидаемые (занятый телефон, неверный пароль) — это `Result::fail('phone_taken')`,
превращающийся в 4xx с машинным кодом и переведённым сообщением. Непредвиденные
ловит `Kernel::handle()`: 500 с деталями при `debug = true`, без деталей в бою,
запись в `storage/logs/`.

## Безопасность

- Наружу отдаются только `assets/` и `index.php` — белым списком, а не
  чёрным. На Railway это делает `Caddyfile` (FrankenPHP), на Apache —
  `.htaccess`. Любой другой адрес уходит в роутер и получает 404.
- Инструменты в `tools/` дополнительно отказываются работать не из
  командной строки (`tools/_guard.php`) — на случай чужого веб-сервера.
- Постоянные данные (база, ключ, токены) — в папке данных
  `$kernel->dataDir()`: `storage/` на хостинге, том на Railway.
- `/health` посторонним показывает только «работает / нет».
- В базе только хеш токена сессии и хеш пароля.
- Перебор пароля ограничен: 5 неудач с одного IP за 15 минут.
- Заголовки `X-Content-Type-Options`, `Referrer-Policy` и
  `frame-ancestors` c Telegram (не `SAMEORIGIN`: веб-версия Telegram
  открывает Mini App во фрейме).

## Когда понадобится вынести модуль в сервис

Признак один: модуль стал узким местом по нагрузке или требует
инфраструктуры, которой нет на общем хостинге (постоянный процесс,
очередь, тяжёлая модель). Тогда его `Domain/` переезжает как есть, а на
месте остаётся реализация того же контракта, ходящая по HTTP. Остальное
приложение изменений не заметит — оно и раньше знало только контракт.

## Резервная копия

Вся база — один файл `level180.sqlite` в папке данных. Скачивать раз в
неделю. Вместе с переменными окружения это полный слепок системы.

## Сквады и соседи (срез 4)

Модуль `squad` — хороший пример того, как модуль живёт, ничего не зная о
соседях. Всё, что ему нужно, он спрашивает событиями, а отвечают те, кто
владеет данными:

| Событие | Кто спрашивает | Кто отвечает | Что если отвечающего нет |
|---|---|---|---|
| `squad.profile_lookup` | Squad | Onboarding | человек не попадает в пул, пока не пройдёт онбординг |
| `squad.activity` | Squad | Checkin | статусы паузы не меняются — не знаем, кто пропал |
| `squad.member_weeks` | Squad | Checkin | командный счёт не пишется |
| `telegram.group_send` | Squad | Telegram | карточки не уходят, метрика первой реакции не стартует |
| `telegram.invite_link` | Squad | Telegram | ссылку модератор вставляет руками |
| `season.scheduled` | Squad | Planning | план не сдвигается на общий день 1 |

И наоборот: `squad.leader_term_completed` слушает Gamification (+250 XP),
`telegram.group_message` публикует Telegram, `onboarding.completed` и
`user.returned` приходят от соседей. Тест `smoke.php` поднимает сквады
вообще без онбординга, чек-ина, очков и Telegram — модуль отвечает, а не падает.

## Тренер, браслет и безопасность (срез 5)

Тренер (`coach`) — самый «любопытный» модуль: ему нужны профиль, чек-ины,
браслет, вес и план. Он не читает ни одной чужой таблицы:

| Что нужно | Как получает | Кто отвечает |
|---|---|---|
| профиль и baseline | событие `coach.context` | Onboarding |
| чек-ины, неделя, серия, помехи | событие `coach.context` | Checkin |
| тренд веса | событие `coach.context` | Wearable |
| дни браслета, медианы | контракт `Wearable` | Wearable (или заглушка) |
| действие и нормы дня | контракт `Planner` | Planning (или заглушка) |
| облегчить план | событие `plan.load_adjust` | Planning |

Облегчение плана хранится в `planning_adjustments` и умножает нормы на
коэффициент < 1 на несколько дней. Сделать план тяжелее этим путём
невозможно по построению: `adjust()` отказывает при коэффициенте ≥ 1.

Безопасность (`safety`) слушает свободный текст (заметка к чек-ину,
сообщения в группе сквада, событие `safety.check_text`) и работает без
тренера. Её помощь возвращается в ответ чек-ина полем `safety`; тренер
в этом случае молчит.

Модель подключается через интерфейс `Coach\Domain\LlmClient`. Реализация
одна — OpenAI-совместимый `/chat/completions`, смена провайдера — смена
`AI_BASE` и `AI_KEY`. В тестах клиент подменяется в контейнере.

## Деньги, управление, метрики, права на данные (срез 6)

- **Доступ к сезону** — контракт `Access` (Billing). Заглушка открывает
  всё: без модуля оплаты продукт бесплатный, а не сломанный. Сквады берут в
  подбор и на замену только людей с сезоном; тренер зовёт модель только
  для них. Нулевой цикл, план, чек-ины и история — бесплатно всегда.
- **Метрики** — Analytics ведёт свой журнал фактов (`analytics_events`) и
  считает активацию, удержание, Kept Week, конверсию. Чужие цифры
  (Return Rate, сквады, тренер, рефералы, сигналы) модули докладывают сами
  по событию `analytics.collect`. У каждой метрики — цель из § 13.
- **Журнал решений** — любой модуль сообщает о решении модератора событием
  `admin.action`, журнал ведёт Admin.
- **Выгрузка и удаление** — `App\UserData::register()`: каждый модуль
  объявляет свои таблицы, ядро собирает выгрузку (`user.export`) и
  удаление (`user.erase`), ничего не зная о модулях. Платежи и журнал
  фактов не стираются, а обезличиваются.

## Фото, лента, созвоны (срез 7)

```
            Feed ──Team──▶ Squad            Calls ──Team──▶ Squad
              │                               │
              └──Media──▶ Media               └──CallProvider──▶ Telegram / Jitsi
```

- **Media** — хранилище без смысла. Принимает фото (`Media::store`) только
  на сервере с `DATA_RESIDENCY=UZ`, проверяет тип по байтам и размер по
  заголовку до распаковки, поворачивает по EXIF, пересжимает в два JPEG без
  метаданных, кладёт в `DATA_DIR/media` под случайными именами. Отдаёт по
  подписанной ссылке (`/api/media/{token}/{thumb|full}?u&e&s`). Сроки
  хранения чистит на `system.tick`.
- **Feed** — смысл: кто в скваде (контракт `Team`), что можно выложить,
  жалобы, поддержка. Подпись проходит `safety.check_text`. Метрики —
  через `analytics.collect`.
- **Calls** — расписание созвонов, ответы, напоминания (`system.tick`).
  Где идёт звонок — контракт `CallProvider`.
- **Squad** реализует `Team` и слушает `calls.scheduled` (засчитывает
  лидеру дело недели) и `system.tick` (пересчёт сквадов).
- **Удаление аккаунта** стирает файлы с диска раньше строк: у
  `UserData::register` появились ключи `before` (файлы) и `map`
  (ссылка на сутки в выгрузке).
- Без сквадов лента и созвоны отвечают «вы пока не в скваде» — шестой
  сценарий отключения в `smoke.php`.

## Интерфейс (редакция 2026)

Один файл `assets/app.js`, экраны — функции. Общие детали: `icon()`
(свои линейные иконки), `ring()` (кольцо прогресса), `tile()` (плитка бенто),
`face()` (кружок с буквой), `navbar()` (нижняя панель главных экранов).
Тема — `data-theme` на `<html>` из Telegram или настроек телефона; все
цвета — токены в `:root` файла `app.css`. Строки оболочки — модуль Web.
