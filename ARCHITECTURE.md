# Архитектура

## Почему не микросервисы

Требование звучало так: «убрать или добавить модуль и чтобы ничего не слетело».
Классические микросервисы дают это ценой отдельных процессов, сети между ними,
своей базы у каждого сервиса и оркестрации. На shared-хостинге за $2–3 это
не запускается, а для одного разработчика умножает работу в разы.

То же свойство даёт **модульный монолит с дисциплиной микросервисов**:
границы такие же жёсткие, а разворачивается как одна папка. Если модуль
когда-нибудь понадобится вынести в отдельный сервис — он к этому уже готов,
потому что не имеет прямых связей с соседями.

## Три уровня

```
┌──────────────────────────────────────────────────────────┐
│  index.php — единственная точка входа                    │
└───────────────────────────┬──────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────┐
│  ЯДРО (app/)  не знает ни одного имени модуля            │
│  Kernel · Container · ModuleRegistry · Events · Router    │
│  Db · Migrator · I18n · Request · Response · Result       │
│  Contracts/ ──── интерфейсы + безопасные заглушки         │
└───────────────────────────┬──────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────┐
│  МОДУЛИ (modules/)  между собой — только события          │
│                     и контракты                           │
│  Health · Identity · [Onboarding · Planning · Checkin ·   │
│  Squad · Coach · Wearable · Gamification · Billing]       │
└──────────────────────────────────────────────────────────┘
```

## Анатомия модуля

```
modules/Squad/
  module.json         паспорт: имя, версия, зависимости, какие события
                      публикует и слушает, префикс таблиц
  Module.php          register() — свои сервисы в контейнер
                      boot()     — подписки на события
  routes.php          свои HTTP-маршруты
  Domain/             логика; ничего не знает про HTTP, возвращает Result
  Migrations/         001_init.sql, 002_… — только свои таблицы
  lang/ru.php
  lang/uz.php
```

Правило владения данными: модуль `squad` владеет таблицами `squad_*` и
только ими. Чужие данные берутся через контракт или приходят в событии.
Никаких `JOIN` через границу модуля — именно это позволяет вырезать модуль
целиком, не сломав соседей.

## Как модули общаются

**События — когда «сообщаю, что произошло».** Издатель не знает, слушает ли
его кто-нибудь, и не ждёт ответа.

```php
// модуль Checkin, ничего не знает про очки
$kernel->events->emit('checkin.recorded', ['user_id' => 7, 'done' => true]);

// модуль Gamification, подписался в boot()
$kernel->events->on('checkin.recorded', function (array $p) use ($kernel) {
    $kernel->container->get(Gamification::class)->award($p['user_id'], 'checkin', 10);
}, 'gamification');
```

Выключили Gamification — чек-ин продолжает работать, просто очки не
начисляются. Слушатель, бросивший исключение, не роняет издателя: ошибка
пишется в лог и видна в `/health`.

**Контракты — когда «нужен ответ».**

```php
$coach = $kernel->container->get(App\Contracts\Coach::class);
$reply = $coach->replyToCheckin($context);   // NullCoach вернёт шаблон
```

## Заглушки — техническая гарантия обещания

`app/bootstrap.php` регистрирует заглушку для каждого контракта **до**
загрузки модулей. Модуль, реализующий контракт, перекрывает её в `register()`.
Если модуль выключен, контейнер отдаёт заглушку, и приложение теряет
возможность, но не падает.

| Контракт | Реализует | Что делает заглушка |
|---|---|---|
| `Auth` | Identity | Возвращает «не авторизован» → защищённые маршруты дают 401 |
| `Coach` | Coach | Отвечает шаблонами, `isLive() = false` |
| `Notifier` | Telegram / Sms | Не отправляет, возвращает `false` |
| `Wearable` | Wearable | Отдаёт `null` по метрикам, `isConnected() = false` |
| `Gamification` | Gamification | Начисляет 0, отдаёт пустой профиль |

`/health` показывает по каждому контракту, кто его реализует и работает ли
он по-настоящему. Это первое, что нужно открыть после правки `modules.php`.

## Порядок загрузки

1. `bootstrap.php` — автозагрузчик, конфиг, контейнер, заглушки контрактов.
2. `discover()` — чтение `module.json`, проверка зависимостей, сортировка.
   Модуль с невыполненной зависимостью выключается, причина попадает в `/health`.
3. `register()` — модули кладут сервисы в контейнер. Обращаться к чужим
   сервисам здесь нельзя: они могут быть ещё не зарегистрированы.
4. `boot()` — подписки на события, маршруты, переводы. Здесь можно всё.
5. `handle()` — маршрутизация запроса.

## Ошибки

Ожидаемые (занятый телефон, неверный пароль) — это `Result::fail('phone_taken')`,
превращающийся в 4xx с машинным кодом и переведённым сообщением. Непредвиденные
ловит `Kernel::handle()`: 500 с деталями при `debug = true`, без деталей в бою,
запись в `storage/logs/`.

## Безопасность

- `config.php`, `modules.php`, `app/`, `modules/`, `tools/`, `storage/`
  закрыты `.htaccess` на двух уровнях.
- База лежит в `storage/db/` — вне досягаемости браузера.
- В базе только хеш токена сессии и хеш пароля.
- Перебор пароля ограничен: 5 неудач с одного IP за 15 минут.
- Заголовки `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`.

## Когда понадобится вынести модуль в сервис

Признак один: модуль стал узким местом по нагрузке или требует
инфраструктуры, которой нет на общем хостинге (постоянный процесс,
очередь, тяжёлая модель). Тогда его `Domain/` переезжает как есть, а на
месте остаётся реализация того же контракта, ходящая по HTTP. Остальное
приложение изменений не заметит — оно и раньше знало только контракт.

## Резервная копия

Вся база — один файл `storage/db/level180.sqlite`. Скачивать раз в неделю.
Вместе с `config.php` это полный слепок системы.
